# 📋 FoxChatRAG-python 阅读计划

> 配合 Java 端（FoxChat-java）交叉阅读，理解完整 gRPC 调用链。

---

## 🎯 核心认知：Java ↔ Python 的两条通道

```
Java (LlmChatServiceImpl)
  ├── gRPC (优先) → Python :50051  ── AIChatService.Chat (流式)
  └── REST (降级) → Python :8000   ── POST /chat/msg (非流式)
```

读py端的正确姿势：**沿着 gRPC 调用链从上往下追**，而不是按文件目录瞎翻！

## 📖 分5步走

---

### 🔹 第1步：协议层（预计 15 分钟）⭐

> **先读懂"合同"，才知道两边在说什么**

| 文件 | 说明 |
|------|------|
| `proto/ai_chat.proto` | **整个系统最核心的"合同"**，不到 80 行 |
| Java侧 `AiChatProto.java` | 对照看 Java 生成的代码（你之前应该已经看过） |

**要点：**

- `ChatRequest` 三个字段：`user_id`, `llm_id`, `msg_content` — **Java 发什么**
- `ChatResponse` 九个字段 — **Python 怎么逐 token 回**：
  - `content` — 单 token 文本
  - `block_type` — `"text"` / `"action"`
  - `is_block_start` / `is_block_end` — 前端渲染分隔
  - `is_final` — 结束标记
  - `emotion` — 情绪标签
  - `sequence` — 断流恢复定位
- `DeleteMemory` — 清记忆的非流式 RPC

---

### 🔹 第2步：gRPC 链路（核心！预计 45 分钟）⭐⭐⭐

> **这是 py 端的"入口"，也是和 Java 耦合最紧的地方**

按数据流方向阅读：

```
Java: GrpcChatClient.streamChat()
  ↓ gRPC network
Python: ai_chat_server.py          ← ① 从这里开始！
  ↓
streaming_tag_parser.py            ← ② token → block_type 解析
  ↓
graph.py → nodes.py                ← ③ LangGraph 编排
  ↓
llm_invoke_service.py              ← ④ 实际 LLM 调用
```

| 顺序 | 文件 | 看什么 |
|------|------|--------|
| ① | `app/grpc/ai_chat_server.py` | **核心入口**。`AIChatServiceImpl.Chat()`：接收 `ChatRequest` → `StreamingTagParser` 解析 token → 流失败降级 `_fallback_chat()` → 通过 `contextvars` 传递 `stream_queue` 绕过 LangGraph checkpointer 序列化 |
| ② | `app/service/chat/parsing/streaming_tag_parser.py` | `<action>` 标签解析器。LLM输出 `"你好<action>挥了挥手</action>再见"` → 拆成 text 块 + action 块，标注 `block_type`、`is_block_start/end` |
| ③ | `app/service/chat/graph/graph.py` | **LangGraph DAG 拓扑**：`START → pre_flight → fetch_memory → parse_memory → classify_intent → [retrieve\|skip] → invoke_llm → [save ‖ format ‖ emotion ‖ summary] → unlock → END` |
| ④ | `app/service/chat/graph/nodes.py` | 每个节点的实现。关键看 `invoke_llm` 节点：**流式模式**通过 `stream_queue` 推 token，**非流式**直接返回完整结果 |
| ⑤ | `app/service/chat/llm/llm_invoke_service.py` | `stream_llm_with_retrieval()` → `litellm.acompletion(stream=True)` → 逐 token yield；`_build_chat_messages()` 构建完整 prompt |

**🔗 对照 Java 侧阅读：**

| Python | Java 对照 |
|--------|----------|
| `ai_chat_server.py::Chat()` | `GrpcChatClient.streamChat()` + `ChatStreamObserver` |
| `ai_chat_server.py::_stream_chat()` | `LlmChatServiceImpl.llmChatStream()` 的 `onToken` callback |
| `ai_chat_server.py::_fallback_chat()` | `LlmChatServiceImpl.fallbackToRest()` |
| `api/chat.py::chat_msg` | `ChatClient.chatMsg()` (Feign 降级) |
| `streaming_tag_parser.py` | `LlmChatServiceImpl` 中 `flushCurrentBlock()` / `buildBlockSnapshot()` |

### 🔹 第3步：记忆架构（预计 40 分钟）⭐⭐⭐⭐

> **这是 py 端最复杂的部分，也是 vibecoding 最容易出 bug 的地方**

按记忆分层从上到下读：

```
A1. 静态锚点    (soul / character_card)
A2. 用户画像    (user_profile / 硬边界)
B.  当前状态    (emotion → current_state)
C.  历史事件    (memory_bank + Chroma summary)
D.  最近窗口    (recent_msg, 最近 4~6 轮)
```

| 顺序 | 文件 | 看什么 |
|------|------|--------|
| ① | `app/service/chat/memory/memory_parser.py` | **5 种记忆的解析入口**：`parse_character_card()`、`parse_core_anchor()`、`parse_user_profile()`、`parse_memory_bank()`、`parse_current_state()` |
| ② | `app/service/chat/state/state_manager.py` | **B 层核心**。RedisJSON 原子更新情绪状态 → 过期机制（`is_expired`）→ 覆盖规则（过期 > 来源等级 > 置信度差值 > 值变化） |
| ③ | `app/service/chat/memory/history_event_retrieval_service.py` | **C 层核心**。BM25(Redis) + Vector(ChromaDB) + FlashRank Rerank **混合检索**。`retrieve_history_events_v2()` → 去重 → 格式化 |
| ④ | `app/service/chat/memory/memory_upload_service.py` | 对话总结 → 事件提取 → 去重入库。每 9 轮触发 |
| ⑤ | `app/service/chat/memory/memory_summary_service.py` | 总结候选四路分流：A2 候选 / 状态候选 / 时间候选 / 事件候选 |
| ⑥ | `app/schemas/current_state.py` + `app/schemas/memory_event.py` | Pydantic 数据模型，对照 ① 理解字段 |

### 🔹 第4步：Prompt 构建与 LLM 策略（预计 30 分钟）⭐⭐

> **决定 LLM "看到什么"的关键层**

| 顺序 | 文件 | 看什么 |
|------|------|--------|
| ① | `app/service/chat/llm/prompt_payload_builder.py` | **统一 Payload 构建器**。3 层处理：空块抑制（`_is_empty_block`）→ 跨层去重 A2>B>C>D（`_suppress_duplicates_across_layers`）→ 冲突优先级（A2 硬边界 vs B/C 层冲突检测 `_enforce_conflict_priority`） |
| ② | `app/service/chat/strategy/base_strategy.py` | LLM 调用策略。`ChatInvokeStrategy()` — 包装 litellm，处理 model name 格式化、api_key 注入 |
| ③ | `app/core/prompts/prompt_manager.py` | Prompt 模板管理器。加载 `.md` 文件 |
| ④ | `app/core/prompts/*.md` | 各种 Prompt 模板：`chat_system.md`（对话主 prompt）、`soul.md`（角色灵魂）、`emotion_classifier.md`、`focus_extractor.md`、`user_profile.md`… |
| ⑤ | `app/service/chat/llm/intent_classifier.py` | 两层意图分类（规则 + 语义），决定走 `retrieve` 还是 `skip_retrieval` |

## ⚠️ Vibecoding 注意事项

既然 py 端大部分是 AI 生成的，读的时候留意这些典型问题：

1. **重复逻辑** — 同一个功能可能在多个 service 里各写了一遍
2. **过度抽象** — 可能有"为了设计模式而设计模式"的代码（比如 `base_strategy.py` 的策略模式是否真的需要？）
3. **错误处理缺失** — AI 生成的代码常常 try-catch 不完整
4. **注释和实际不一致** — README 里列的文件名可能和实际代码对不上（README 写了 `candidate_router_service.py` 但实际文件不存在）
5. **死代码** — 有些函数可能定义了但从未被调用

## 🗺️ 完整调用链路图（速查）

```
前端 WebSocket
    ↓
Java: LlmChatServiceImpl.llmChatStream()
    ↓ CompletableFuture.runAsync
Java: GrpcChatClient.streamChat()
    ↓ gRPC (proto/ai_chat.proto)
    ═══════════════════════════════
Python: AIChatServiceImpl.Chat()
    ↓
StreamingTagParser
    ↓
LangGraph (graph.py)
  ├── pre_flight        → 轮数初始化
  ├── fetch_memory      → Redis pipeline 批量拉取
  ├── parse_memory      → 5种记忆解析
  ├── classify_intent   → 意图分类 (规则+语义)
  ├── retrieve/skip     → BM25+Vector+Rerank / 跳过
  ├── invoke_llm        → litellm.acompletion(stream=True)
  ├── ┌─ save_message   → 存入 Redis recent_msg
  │   ├─ format_output  → <action>标签解析
  │   ├─ classify_emotion → 情绪更新 current_state
  │   └─ trigger_summary → 9轮触发总结
  └── unlock
    ↓
ChatResponse (逐token, gRPC stream)
    ═══════════════════════════════
    ↓ gRPC
Java: ChatStreamObserver.onNext()
    ↓ onToken callback
Java: LlmChatServiceImpl (SSE emitter)
    ↓ SSE event
前端 WebSocket/SSE
```
